# ADR: Lazy-generated, disk-cached preview tier for the lightbox
Date: 2026-08-21
Status: accepted

## Context

Guests complained that photos looked blurry/pixelated when opened full-screen
in the gallery lightbox. Root cause: the lightbox was reusing the
gallery-grid thumbnail (`GET /api/v1/events/{event_id}/photos/{photo_id}/thumbnail`,
served from `Photo.thumbnail_path`, generated by
`face_pipeline._generate_thumbnail` — max 600px wide, WebP quality=85) and
upscaling that 600px image to fill the viewport.

The system already has two image tiers:

- **Thumbnail** (600px, quality 85) — gallery grid, generated synchronously
  inside the async face-processing pipeline (`face_pipeline._run_pipeline`),
  right after face detection, for every uploaded photo.
- **Original** (untouched upload) — served by `/download` and the ZIP
  endpoints (`photo_actions.py`, `zip_streaming.py`).

There was no third, medium-resolution tier suitable for full-screen viewing
that doesn't ship the full multi-megabyte original.

Two ways to add one:

1. Generate the new tier eagerly, alongside the thumbnail, inside
   `face_pipeline._run_pipeline`.
2. Generate it lazily, on first request, and cache the result to disk.

Eager generation was ruled out for two reasons:

- It adds CPU/IO work to the same code path the upload response already
  depends on being fast and non-blocking (constraint 1 — face processing must
  not block upload; adding more per-photo image work to that background task
  increases processing latency for every photo, including ones a guest never
  opens full-screen).
- Every already-uploaded photo across every existing event would need a
  backfill migration/script to generate the new asset, since there's no
  "reprocess just the derived images" path that doesn't also mean touching
  face data — a large one-off job with no natural trigger to run it against
  photos uploaded before this change shipped.

## Decision

Add a new endpoint, `GET /api/v1/events/{event_id}/photos/{photo_id}/lightbox`,
that lazily generates and disk-caches a medium-resolution preview:

- On a cache miss, reads the original from `photo.storage_path`, applies
  `ImageOps.exif_transpose` (mirrors the same orientation fix already used by
  `_generate_thumbnail`, so previews aren't rendered sideways), resizes so
  the longest edge is at most 2000px (never upscales a smaller original),
  converts to RGB, and saves as WebP quality=90.
- The cache path is derived deterministically from `event_id`/`photo_id`
  (`events/{event_id}/previews/{photo_id}.webp`, mirroring the `thumbs/`
  convention) — no new DB column, no backfill. On a hit, the cached file is
  served directly.
- Generation runs off the event loop via `asyncio.to_thread`, and is written
  to a unique temp file then atomically renamed into place, so a concurrent
  request during generation never observes a partial file.
- Auth/scoping mirrors the existing `/thumbnail` and `/download` routes in
  `app/routers/gallery.py`: guest access via `get_validated_guest_event`,
  scoped to `event_id` (constraint 3 — no cross-event leakage).

This gives a three-tier strategy: thumbnail (grid) → lightbox preview
(full-screen viewing) → original (download/ZIP), each sized for its actual
use.

**Naming note:** the route is `/lightbox`, not `/preview`, because
`GET /api/v1/events/{event_id}/photos/{photo_id}/preview` already exists in
`app/routers/photos.py` — an unrelated, photographer-only endpoint (gated by
`get_event_with_photographer_access`) that just re-serves `thumbnail_path`
for the photographer dashboard's photo grid. Reusing that path would have
silently collided with it (whichever router `main.py` registers first wins;
the other route becomes unreachable dead code) rather than raising an error,
which is exactly the kind of failure mode worth naming around instead of
risking.

## Options Considered

| Option | Pros | Cons |
|--------|------|------|
| Precompute during the face pipeline (eager) | One code path generates all derived images; no lazy-generation latency on first view | Slows the async pipeline for every photo, including ones never viewed full-screen; requires a backfill migration/script for already-uploaded events |
| Lazy generation, cached to disk (chosen) | No upload/pipeline slowdown; no backfill — works for existing photos on first request; only pays the generation cost for photos guests actually open full-screen | First lightbox open per photo pays generation latency (one-time; cached after); a second concern to keep in mind alongside the pipeline's thumbnail generation |
| Lazy generation, no disk cache (regenerate every request) | Simplest code, no cache invalidation to think about | Every lightbox open re-decodes/re-resizes the original — wasteful CPU on a single-VM deployment, defeats the purpose of a cheap-to-serve tier |
| Client-side upscaling/blur-free CSS tricks on the existing thumbnail | No backend change | Does not fix the underlying resolution loss; guests are viewing genuinely low-detail pixels no matter how they're rendered |

## Consequences

- Three image tiers now exist, each with a distinct generation trigger:
  thumbnail (eager, part of the face pipeline, `face_pipeline.py`), lightbox
  preview (lazy, on-demand, `gallery.py`/`services/gallery.py`), original
  (never transformed). Anyone adding a fourth derived-image use case should
  default to the lazy+cache pattern unless there's a specific reason the
  pipeline needs to own it.
- No DB migration was needed and none is needed for already-uploaded events —
  the cache path is derived, not stored. If the preview generation
  parameters change later (e.g. a different max edge or quality), cached
  files won't self-invalidate; a path/version suffix would need to change to
  force regeneration.
- The `/preview` vs `/lightbox` naming split means there are now two
  differently-shaped "preview-ish" endpoints for the same photo
  (`photos.py`'s dashboard-facing thumbnail-relabeled-as-preview, and
  `gallery.py`'s guest-facing genuine medium-resolution preview). This is a
  pre-existing naming inconsistency this change works around rather than
  fixes; renaming/consolidating the photographer-dashboard route is out of
  scope here since it would touch the frontend dashboard's contract.
